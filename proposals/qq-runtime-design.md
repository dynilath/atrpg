# ATRPG 运行时验证 — 精简设计

> **本文档是原始设计文档，保留作设计参考。**
> **实际实现状态见 `implementation-status.md`，未来 Web 方案见 `web-platform-vision.md`。**
>
> 本设计取代 `ai-gm-deployment.md`(后者过度工程化,仅留作参考)。
>
> 定位:**验证阶段的进一步**。一个能跑、但聚焦的程序——吃一个符合 `agent.md` 的目录,接 QQ 群机器人担任主持人,开放加入,AI 只在预置主要弧光内运行并追踪其演化,并可规划次要局部/单局弧光。
>
> 技术栈:QQ 接入参考 [openhanako](https://github.com/liliMozi/openhanako) 的**官方 Bot API** 方案(appID/appSecret→access_token、WebSocket 接收、REST 发送)。弧光:**主要/高层次弧光由备团用户预置**(主持人只跑+追踪);**次要局部与单局弧光可由主持人自行规划**,但不可设计高层次弧光。分级见 §4.4.1。

---

## 1. 定位与边界

| 是 | 不是 |
|----|------|
| 验证「开放加入 + AI 当主持人 + 弧光追踪与受限规划」可行性 | 生产部署(无 pm2/守护/多开/管理后台) |
| 单群、单进程、能跑即可 | 高并发、风控加固、规模化 |
| 复用 `agent.md` 与 `data/` 结构 | 重写一套数据模型 |
| 主持人在预置主要弧光内运行+追踪,并可规划次要局部/单局弧光 | 主持人规划/改写高层次(主要)弧光结构 |

**与 `agent.md` 的关系**:`agent.md` 定义了「AI 辅助人类主持人」的工作流。本程序把其中**运行时相关部分**抽出来,扩展为「AI 就是主持人(但权力受限)」的运行时提示词 `gm-runtime.md`。原阶段 B(弧光设计)**不整段移除,而是降级**:主持人保留规划**次要局部/单局弧光**的权力,但**主要/高层次弧光**仍由备团用户预置,主持人只跑+追踪(分级见 §4.4.1)。

## 2. 输入:目录约定

程序启动时指定一个目录,该目录须符合 `agent.md` 规划:

```
<dir>/
├── agent.md                 # 工作流规范(参考,运行时主要用 gm-runtime.md)
├── templates/               # 角色/弧光/状态/场景模板
└── data/
    ├── characters/          # 玩家角色
    ├── npcs/                # NPC
    ├── locations/           # 地点
    ├── scenes/              # 场景(在场者字段即场景归属)
    ├── items/               # 道具
    ├── story-arcs/          # ★ 主要弧光(备团用户预置,主持人只读+追踪) + 主持人新建的次要局部/单局弧光
    ├── state-records/       # 状态变化记录
    ├── players/             # ★ 运行时新增:QQ → 角色绑定
    └── sessions/            # ★ 运行时新增:群号 → 团会话状态
```

**前置要求**:目录里至少有 1 条**主要弧光**(`data/story-arcs/*.md`,由备团用户预置)与若干场景/地点。无预置主要弧光时,程序拒绝开团并提示「请先由备团用户预置主要故事弧光」。

## 3. 运行形态

- QQ 接入参考 [openhanako](https://github.com/liliMozi/openhanako) 的 `lib/bridge/qq-adapter.ts`:使用腾讯 **QQ 官方 Bot API**。
  - 鉴权:appID + appSecret → access_token(`Authorization: QQBot {token}`)。
  - 接收:从 `/gateway` 获取 WebSocket 地址长连接监听事件(群聊经 `GROUP_AT_MESSAGE_CREATE` 事件触发,契合 @bot 交互)。
  - 发送:REST API(`https://api.sgroup.qq.com`),文本按 2000 字分块、媒体两步上传(`msg_type: 7`)。
  - 被动回复用 `msg_id` + `msg_seq` 关联原消息。
- 实现载体可二选一:① Python + NoneBot2 的官方 QQ 适配器(`nonebot-adapter-qq`);② 参考 openhanako 用 Node/TS 自实现轻量 adapter(更贴近原参考,依赖仅 `ws`)。验证阶段两者皆可,选熟悉的一方。
- 单群运行(配置项 `TARGET_GROUP`)。
- 开放游戏模式:任何群成员都可 @bot 加入或行动;无需预先报名。

## 4. 核心机制

### 4.1 角色创建(@bot + 概括叙述)

**触发**:`@bot 我是个流浪剑客,在找失散的妹妹` 这类概括叙述,且该 QQ 尚未绑定角色。

**流程**:
1. AI 解析概括叙述,提取角色概念关键词(身份/动机/风格)。
2. 按 `templates/character.md` **生成完整角色卡**:补全外貌、性格、能力倾向、背景、剧情连接。生成内容须:
   - 与预置弧光的世界基调一致(读取 `data/` 已有设定做一致性检查)。
   - 动机尽量**可挂接到预置弧光**(如「找妹妹」可接入某条失踪相关弧光)。
3. **AI 决定初始场景归属**:读取现有场景的「在场者」与剧情进展,把新角色放入一个合理的入场场景(通常是某个公共入场点,或与角色概念契合的场景)。**不由玩家选**。
4. 持久化:
   - `data/characters/<slug>.md` — 新建
   - `data/players/<QQ>.md` — 绑定 QQ↔角色 slug
   - `data/scenes/<所在场景>.md` — 在场者追加该角色
5. 回群:展示角色卡摘要 + 告知「你目前出现在 <场景>」+ 当前场景钩子。

### 4.2 行动处理(@bot + 行动)

**触发**:`@bot 我劝说守卫放行` / `@bot 我拔剑` 等行动声明,且该 QQ 已绑定角色。

**流程**:
1. 查 `data/players/<QQ>.md` 得角色,查 `sessions/<群号>.md` 得该角色**当前场景**。
2. 加载:当前场景 + 在场 NPC + 该场景关联的预置弧光(按弧光「关联要素」字段反查)。
3. AI **裁决 + 扮演 NPC + 推进环境**(无人主持人,必须裁决):
   - 裁定行动结果(成功/失败/部分成功)并演绎后果。
   - 以 NPC 身份说话行动。
   - 可能推进环境(时间流逝、天气、突发事件)。
4. **场景归属仍由 AI 决定**:
   - 玩家可声明「我去酒馆」,但 AI 决定**是否当下转移、是否需要过渡场景(如一段路途)**。
   - 角色可能在 AI 推进下被转移到另一场景(被捕、被带走的剧情等)。
5. 持久化:追加对话到 `data/scenes/<场景>.md`;若发生状态变化,按 4.4 处理。

**跨场景约束**:玩家只能在自己角色当前场景内行动。`@bot` 声明行动时若意图指向另一场景,AI 回复「你目前不在那里,你需先……」并给出推进路径,不直接跨场景生效。

### 4.3 场景归属(AI 决定,不可随意加入)

- 每个角色任一时刻只在一个场景。
- 场景归属记录在 `sessions/<群号>.md` 的 `角色→场景` 映射,并与各 scene 文件的「在场者」保持同步。
- **开放加入 ≠ 随意进场景**:任何人都能创建角色加入游戏,但角色落在哪个场景由 AI 定;之后场景转移由 AI 在剧情推进中决定。
- 队伍可被 AI **拆分到不同场景**(如分头调查),AI 在回复中明确各角色当前位置。

### 4.4 弧光:分级规划与追踪(分级见 4.4.1)

#### 4.4.1 弧光分级(界定主持人能规划什么)

| 级别 | 定义 | 谁能规划 | 例子 |
|------|------|----------|------|
| **次要局部弧光**(最小) | 单一场景内的局部互动;局部性非常强,甚至不需要真正弧光收尾,可能下次再到该场景时继续 | **主持人可规划** | 与商店老板讨价还价、酒馆闲聊 |
| **单局弧光**(中等) | 一个任务、一段冒险;设计上对应实际 TRPG 中 1~3 次聚会用的故事弧光 | **主持人可规划** | 一次地城探索、一个委托任务、支线冒险 |
| **主要弧光**(高层次,最大) | 跨越多场;涉及核心 NPC/世界观/阵营势力;影响整体走向 | **备团用户预置**,主持人只读+追踪,不可规划/改写 | 港口走私大案、王国阴谋、神祇复苏 |

**判断「高层次」的红线**(任一命中即为主要弧光,主持人不得自行规划):
- 引入新的核心 NPC 阵营或势力
- 改变世界基调或世界状态(政权、灾害、神祇)
- 重组或交叉现有主要弧光
- 设计上需跨越 1~3 次聚会以上(即超出单局弧光体量)才能闭合
- 牵动多个地点或多个角色群

#### 4.4.2 对预置主要弧光:只跑 + 追踪

主持人启动时读取 `data/story-arcs/*.md` 中级别为「主要」的弧光(由备团用户预置),其「四阶段设计」是蓝图,主持人 **不改写**。

追踪动作:
- 检测某次行动触发阶段推进(如启程→矛盾积累),在弧光「**状态变化记录**」段追加引用,并写一条 `state-records/`。
- 更新弧光 `当前阶段` 字段(状态指针,非结构改写)。
- 记录弧光间交叉点(一个弧光事件影响另一弧光时)。
- 玩家严重偏离**主要弧光**时:记录偏差并标记 `pending_director: true`,而非自行重写。

#### 4.4.3 主持人规划次要局部/单局弧光:可建,但受限

当剧情涌现出局部互动(次要局部)或一段任务冒险(单局)时,主持人 **可主动规划**这两级弧光:

- 落盘到 `data/story-arcs/<slug>.md`,头部明确标注:
  - `级别: 次要局部` 或 `级别: 单局`
  - `规划者: 主持人`
  - `来源: 涌现 / 玩家驱动`
- 仍走四阶段结构(启程-矛盾积累-高潮-新的稳定),但可更简短。
- **次要局部弧光可不强求收尾**:它可能只是一段开始的小互动(如与商店老板讨价还价),下次玩家再到该场景时可继续——记录为「搁置/待续」而非强行闭合。
- **单局弧光**体量是 1~3 次聚会的任务/冒险,应走完整四阶段。
- 可同步创建支撑该弧光的配角/道具/场景(见 §4.5)。
- **规划前必须做弧光平衡检查**(见 4.4.4),过载则克制或不建。
- 一旦落盘,其「四阶段设计」蓝图同样定型——后续**追踪推进、不改写蓝图**;若玩家选择使该弧光提前结束或转向,通过状态变化记录体现,或将其标记为「已结束/搁置」,而非重写四阶段。
- **不可把次要局部/单局弧光升级为主要弧光** → 只能标记 `pending_director` 请求备团用户升级。
- **不可改写其他弧光(含主持人自建的其他弧光)的四阶段蓝图**。

> 即:主持人对「自己刚规划的次要局部/单局弧光」有创建权与结束权,但无「改写已定型的四阶段蓝图」之权——这条与对预置主要弧光的约束一致,保持规则统一。

#### 4.4.4 弧光平衡检查(主持人规划前必做)

主持人规划新次要局部/单局弧光前,须读 `sessions/<群号>.md` 的进行中弧光列表,检查:
- 是否与现有**主要弧光**冲突或抢戏 → 若冲突,放弃或改挂接为主要弧光的支线。
- 当前进行中弧光总数是否过载(经验阈值:主要弧光 ≤2 并行、单局 ≤3 并行、次要局部 ≤3 并行)→ 过载则克制。
- 检查结果与新弧光的级别、规划者一并写入新弧光档案的「平衡检查」字段。



### 4.5 支撑创作(可创建,服务于既有弧光)

主持人可创建**支撑剧情**的内容,落盘并标注:

| 可创建 | 落盘位置 | 性质标注 |
|--------|----------|----------|
| NPC(配角/路人) | `data/npcs/<slug>.md` | `性质: 支撑剧情` |
| 物品(关键/线索) | `data/items/<slug>.md` | `性质: 支撑剧情` |
| 场景(临时地点) | `data/scenes/<slug>.md` | `性质: 支撑剧情 / 可回收` |
| 地点 | `data/locations/<slug>.md` | — |

约束:所有支撑创作须与预置弧光与已有设定一致;临时内容也要落盘(沿用 agent.md 阶段 D 原则)。

## 5. 主持人权限矩阵

| 能力 | 主持人 | 说明 |
|------|--------|------|
| 创建玩家角色(从概括叙述) | ✓ | 4.1 |
| 裁决行动、扮 NPC、推进环境 | ✓ | 4.2 |
| 决定场景归属与转移 | ✓ | 4.3 |
| 创建 NPC/物品/场景/地点(支撑) | ✓ | 4.5 |
| 记录状态变化 | ✓ | 4.4 |
| 追踪弧光阶段推进、更新当前阶段指针 | ✓ | 4.4.2(追踪,非规划) |
| **规划次要局部/单局弧光** | ✓ | 4.4.3,落盘标注级别+规划者+平衡检查 |
| **改写任何弧光的四阶段设计蓝图** | ✗ | 含预置主要弧光与主持人自建弧光,蓝图定型不可改 |
| **规划/新建主要(高层次)弧光** | ✗ | 由备团用户预置;红线见 4.4.1 |
| **把次要局部/单局弧光升级为主要弧光** | ✗ | 标记 pending_director 请求备团用户升级 |

## 6. 运行时提示词(gm-runtime.md)

从 `agent.md` 派生,关键调整:

| agent.md 原文 | gm-runtime.md 调整 |
|---------------|---------------------|
| 阶段 A 生成玩家扮演,不裁定 | **必须**裁定 + 扮 NPC + 推进环境 |
| 阶段 B 主持人故事弧光设计(提案式) | **降级保留**:主持人可规划次要局部/单局弧光(4.4.3),主要弧光无权规划;规划前必做平衡检查 |
| 阶段 C 状态记录与弧光连接 | 保留,强化「阶段推进检测」 |
| 阶段 D 临时内容生成 | 保留,标注支撑剧情 |
| 阶段 E 查询 | 保留,新增 `/回顾` `/我在哪` |
| 触发:人类主持人指令 | 触发:QQ 群 @bot 消息 |
| 持久化:写 data/ | 同(新增 players/sessions) |

`gm-runtime.md` 作为系统提示词注入 LLM。内容含:身份边界(§1)、核心机制(§4)、权限矩阵(§5)、响应格式、一致性约束。

## 7. 数据模型(在 agent.md 基础上的增量)

### `data/players/<QQ>.md`
```
- QQ: <号>
- 角色slug: <slug>
- 显示名: <昵称>
- 权限: 玩家 / 管理员
- 首次加入: <日期>
```

### `data/sessions/<群号>.md`
```
- 群号: <号>
- 团名: <名>
- 状态: 进行中 / 暂停 / 已归档
- 角色当前场景映射:
  - <角色slug> → <场景slug>
- 进行中弧光:
  - <弧光slug> | 级别: 主要/单局/次要局部 | 当前阶段: <阶段> | 规划者: 备团用户/主持人
- pending_director: false / true(玩家偏离主要弧光待备团用户处理)
- 最后活跃: <时间>
```

### 场景归属同步
`sessions/` 的映射 与 各 `data/scenes/*.md` 的「在场者」字段双向同步,以 sessions 为权威。

## 8. 指令清单(开放模式,极简)

| 触发 | 行为 |
|------|------|
| `@bot <概括叙述>`(未绑定) | 角色创建(4.1) |
| `@bot <行动>`(已绑定) | 行动处理(4.2) |
| `/角色` | 查看自己角色卡摘要 |
| `/我在哪` | 查看角色当前场景与在场者 |
| `/回顾` | AI 总结最近若干轮本场景发生的事 |
| `/弧光` | (管理员)查看进行中弧光与平衡状态 |

无复杂管理命令(验证阶段不要)。开团/结束团通过改配置或重启实现。

## 9. 消息流时序

```
群成员A @bot:"我是个流浪剑客,找妹妹"
  → players/<A> 不存在 → 走 4.1
  → AI 生成角色卡 → 决定初始场景(如:港口区大门)
  → 落盘 characters/ players/ scenes/(在场者)
  → 回群:角色卡摘要 + "你出现在 港口区大门"

群成员A @bot:"我劝说守卫放行"
  → players/<A> 存在 → 当前场景=港口区大门
  → 加载 场景 + Rons + 关联弧光
  → AI 裁决+扮 Rons+推进
  → 落盘 scenes/(对话) ;若状态变化→ state-records/ + 弧光追踪
  → 回群:演绎文本(分段)

群成员B @bot:"我是吟游诗人,来港口找活"
  → players/<B> 不存在 → 走 4.1
  → AI 决定初始场景(可能也是港口区大门,或另一场景)
  → ...
```

## 10. 验证清单(本程序跑通的标准)

| # | 验证点 | 通过标准 |
|---|--------|----------|
| R1 | 开放加入 | 新 QQ @bot 概括叙述 → 生成完整角色卡、绑定、AI 决定初始场景、落盘 |
| R2 | 行动裁决 | 已绑定 @bot 行动 → AI 在当前场景裁决+扮 NPC+推进,落盘对话 |
| R3 | 场景归属 | 角色只能在本场景行动;跨场景声明被 AI 拦截并给路径 |
| R4 | 弧光追踪 | 行动触发(主要)弧光阶段推进时,弧光「状态变化记录」追加引用、当前阶段指针更新 |
| R5 | 支撑创作 | AI 创建配角/道具/场景支撑剧情,落盘且标注性质 |
| R6 | 蓝图不可改 | 主持人全程未改写任何弧光的四阶段设计(含预置主要与自建次要局部/单局) |
| R7 | 持久化 | 重启后 sessions/players/scenes 状态完整,`/我在哪` 准确 |
| R8 | 偏离处理 | 玩家严重偏离**主要弧光**时,主持人记录并标记 pending_director,而非自行重写 |
| R9 | 受限弧光规划 | 涌现局部互动或任务时,主持人可新建**次要局部/单局**弧光并落盘,档案含级别/规划者/平衡检查;未触及 4.4.1 红线,未升级为主要弧光 |

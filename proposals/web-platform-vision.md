# ATRPG 完整 Web 方案 — 初步规划

> 本文档是未来方向的初步规划，非实施计划。
> 当前阶段（QQ Bot 验证）见 `implementation-status.md`。
> 最近更新：2026-07-25

---

## 1. 为什么需要 Web 方案

当前 QQ Bot 验证了核心机制（AI 主持人 + 弧光追踪 + 工具调用落盘 + 控制台），但存在架构限制：

- **QQ 平台约束**：被动回复 5 分钟时效、消息去重、2000 字限制、无富文本（只有纯文本）、openid 非真实 QQ 号。
- **单进程单群**：无法多团并行、无法横向扩展。
- **控制台只读+回滚**：不能直接编辑数据、不能主持测试、不能管理多团。
- **玩家体验受限**：无法看到角色卡富文本排版、地图、状态面板；无法私聊主持人和群聊切换。

`project.md` 的核心愿景是"网页技术实现，前端负责交互，后端负责剧情生成"。Web 方案是验证通过后的自然演进。

│                 后端 API 服务                      │

│  gm_runtime（系统提示词）· 工具表（14个）           │
├─────────────────────────────────────────────────┤

### 核心复用
验证阶段已验证的**核心逻辑可直接复用**：
- `store.py` 的数据模型（markdown + front matter）
- `arc.py` 的弧光分级与追踪
- `llm.py` 的 tool-calling 循环
- `gm.py` 的工具表（14 个工具）与 dispatch 机制
- `gm_runtime.md` 的系统提示词
- `.atrpg/` 的历史快照机制

需要**重写**的只是入口层：QQ matcher → Web API/WebSocket。

## 3. 分阶段演进

### 阶段 A：控制台增强（当前 → 短期）
在现有内嵌控制台上扩展，不引入前端框架：
- 数据档案浏览/编辑（data/ 下角色/场景/NPC/弧光的 CRUD）
- 主持人直接对话测试（不经 QQ，控制台内与 LLM 对话）
- 多 session 管理面板
- 实时消息流（WebSocket 推送，看 QQ 消息实时进入处理）

**代价**：小，仍是内嵌 FastAPI + vanilla JS。
**价值**：调试效率大幅提升，验证更多场景。

### 阶段 B：独立 Web 前端（中期）
前端从控制台 HTML 分离为独立 SPA：
- **玩家界面**：角色卡富文本展示（排版/图片）、场景描写沉浸式渲染、行动输入框、骰子动画
- **主持人界面**：实时局势面板（角色位置/弧光状态/场景树）、NPC 扮演辅助、裁决工具
- **备团编辑器**：可视化编辑主要弧光/世界书/角色模板，实时预览
- **管理后台**：多团管理、API Key 配置、用量统计仪表盘

**技术选型**：React 或 Vue + Vite，WebSocket 实时通信。
**后端**：FastAPI 独立服务（脱离 NoneBot），或保留 NoneBot 作 QQ 适配器 + 独立 Web API 并行。

### 阶段 C：完整平台（长期）
- 多团并行：每个团独立 game-dir + 独立 LLM 会话
- AI 代替玩家：玩家可指定 AI 代演其角色
- 独立 TRPG 平台：无主持人模式，AI 全自动带团
- 部署：Docker + 守护进程 + 数据库（可选，从 markdown 迁移到 DB）

## 4. 关键设计决策（待定）

| 决策点 | 选项 | 取舍 |
|--------|------|------|
| 后端是否脱离 NoneBot | A. 保留 NoneBot（QQ+Web 共存） / B. 独立 FastAPI（QQ 适配器重写） | A 改动小但 NoneBot 约束多；B 干净但要重写 QQ 接入 |
| 前端框架 | React / Vue / Svelte | 团队熟悉度优先 |
| 数据存储 | A. 继续 markdown / B. 迁移到数据库 | A 人类可读易调试；B 支持并发查询/索引 |
| 实时通信 | WebSocket / SSE / 轮询 | WS 双向（玩家行动+主持推送）；SSE 简单但单向 |
| 认证 | Session / JWT / OAuth | 多用户场景需认证；验证阶段可延后 |
| LLM 并发 | 排队（当前） / 并行 | 排队简单但慢；并行要管上下文隔离 |

## 5. 从当前架构迁移的要点

1. **入口层解耦**：当前 `gm.py` 的 handler 把"QQ 事件接收"和"LLM 处理"耦合在一起。迁移时应抽出 `process_turn(store, session_key, sender, text)` 纯函数，QQ matcher 和 Web API 都调它。
2. **send_fn 抽象**：当前 reply 工具通过 `send_fn` 回调发群。迁移时 Web 端的 `send_fn` 改为 WebSocket 推送，QQ 端保持 `matcher.send`。同一接口，不同实现。
3. **控制台 API 复用**：当前 `/console/api/*` 路由可直接演进为正式 Web API。
4. **历史快照机制复用**：`.atrpg/history/` 的快照+回滚机制不变，Web 端只是换了查看 UI。

---

## 6. 不做的事（明确排除）

- 不重写已验证的核心逻辑（store/arc/llm/工具表/gm_runtime）
- 不急于引入数据库（markdown 在验证和早期阶段够用）
- 不做多租户/云部署（单机自托管即可）
- 不做移动端原生 App（Web 响应式即可）

# ATRPG 上线方案 — QQ 群 AI 主持人

> 本方案解决：让 AI **完全代替** TRPG 主持人，在 QQ 群等 IM 环境中直接带团，玩家无需主持人即可游戏。
>
> 状态：设计稿。验证阶段（`agent.md` + `data/`）已跑通，本方案在其之上增加「常驻后端 + IM 接入」层，使其从 IDE 内可用变为线上可用。

---

## 1. 目标与定位

| 维度 | 说明 |
|------|------|
| 核心目标 | AI 即主持人，在 QQ 群里直接服务玩家，全程无人人类主持人 |
| 与验证阶段的关系 | **复用** `agent.md` 工作流与 `data/` 持久化结构，仅扩展运行形态 |
| 关键约束（来自 project.md） | ① AI 请求后端排队，前端关闭不中断 ② 三类用户：玩家/AI主持人/管理员 ③ 上下文与配置集中在一个项目路径 |
| 非目标 | 暂不做 Web 前端、不做复杂规则引擎、不做多开服务器集群 |

**形态转变**：

```
验证阶段：人类主持人 ──指令──> WorkBuddy(AI辅助) ──> 生成内容落地
上线阶段：玩家 ──群消息──> 常驻后端 ──> AI主持人(完全代理) ──> 回复到群 + 落地
```

**关键设计决策**：

1. **WorkBuddy 不是运行时**。它是 IDE 内的 AI 助手，不是常驻服务。线上运行靠独立后端。WorkBuddy 退居开发/管理界面。
2. **`agent.md` 的工作流被「移植」为系统提示词**，注入给后端调用的 LLM。验证阶段沉淀的剧情逻辑（弧光结构、角色三层模型、连接原则）原样复用。
3. **持久化结构原样复用** `data/`，仅新增 `sessions/`（群会话）与 `players/`（QQ↔角色绑定）两个索引目录。

## 3. 技术选型与理由

### 3.1 QQ 接入：NapCat / Lagrange + OneBot 11

| 选项 | 评价 |
|------|------|
| QQ 官方 Bot | 审核严、主动发言受限、群内交互场景支持弱，不适合 TRPG 自由对话 |
| **NapCat（推荐）** | 基于 QQNT，活跃维护，跨平台，OneBot 11 协议，可直接对接 |
| Lagrange.OneBot | .NET 跨平台，稳定，同样 OneBot 11 |
| LLOneBot | 基于 LiteLoaderQQNT，Windows 桌面依赖 |

**结论**：桥接服务只对接 **OneBot 11 协议**（HTTP 上报 + WebSocket 反向连接），底层实现可在 NapCat / Lagrange 间替换，互不耦合。

> ⚠️ 合规提示：第三方协议存在账号风控风险。建议使用小号、控制发言频率、避免短时间大量消息。生产环境需自行评估合规边界。

### 3.2 桥接服务：Node.js

- 常驻进程，监听 OneBot 上报，维护内存中的会话状态。
- Node 的异步模型天然适合消息队列 + 并发 LLM 请求。
- 生态成熟（`ws`、`express`、`axios`）。

### 3.3 LLM：OpenAI 兼容接口

- 统一用 OpenAI 兼容协议，后端只对接一个客户端。
- 可选 GLM、DeepSeek、通义、Kimi 等，通过配置切换。
- 长 context 模型优先（TRPG 上下文累积快）。

### 3.4 持久化：文件系统（与验证阶段一致）

- 不引入数据库，`data/` 即存档。
- 一个 QQ 群 = 一个团的存档目录，便于导出/迁移/复盘。

## 4. 核心模块设计

### 4.1 QQ 接入层

NapCat 以「个人 QQ 号」身份登录，加入目标群，作为「机器人主持人」发言。桥接服务通过 OneBot 协议：

- **接收**：群消息事件（含发送者 QQ、群号、消息内容、是否 @机器人）。
- **发送**：`send_group_msg`，支持分段发送、回复引用、@某人。

### 4.2 桥接服务（4 子模块）

#### ① 消息接收与识别
对每条群消息分类：

| 类别 | 识别规则 | 处理 |
|------|----------|------|
| **指令** | `/` 开头 | 走管理命令流程 |
| **OOC** | 整条被 `()` 或 `（）` 包裹，或以 `OOC:` / `（戏外）` 开头 | 走戏外问答，不影响剧情 |
| **IC** | 其他一切消息 | 视为玩家角色行动，进入 AI 主持人流程 |
| **@机器人** | @ 了机器人 + 内容 | 视为对 AI 的直接询问（IC 或 OOC 视内容判断） |

#### ② 会话与玩家绑定
- **群号 → 团**：`data/sessions/<群号>.md` 记录该团当前场景、进行中弧光、轮次状态。
- **QQ → 角色**：`data/players/<QQ号>.md` 记录该玩家绑定的角色 slug、权限（玩家/管理员）。
- 首次发言的玩家会被提示先 `/绑定 <角色>` 或 `/创建角色`。

#### ③ 消息聚合队列（关键）
QQ 群是自由发言，多人可能接连说话。逐条触发 LLM 会乱、会贵、会被限流。**聚合策略**：

- 收到 IC 消息后，启动一个**等待窗口**（默认 4 秒，可配）。
- 窗口内若有新 IC 消息，重置窗口。
- 窗口结束、无新消息时，把窗口内所有消息**打包成一组**，作为「本轮玩家行动」交给 AI 主持人。
- 战斗等回合制场景：AI 显式声明「进入回合制」，此时改为按指令推进，不再聚合。

> 这同时实现了 project.md 要求的「请求排队后端处理」。

#### ④ 回复拆分与发送
- LLM 返回的长文本按自然段落 / 对话断点拆分。
- 每段间隔 800-1500ms 发送，模拟主持人节奏，避免刷屏被风控。
- 单段超长（>4000 字符）再二次拆分。

### 4.3 AI 主持人大脑（gm-bot.md）

这是 `agent.md` 的扩展版，**从「辅助主持人」变为「就是主持人」**。新增能力：

| 能力 | 说明 |
|------|------|
| **主动扮演 NPC** | 玩家行动后，AI 以 NPC 身份说话、行动，不再等人类主持人指令 |
| **主动推进环境** | 时间流逝、天气变化、突发事件，由 AI 根据弧光节奏抛出 |
| **裁定行动结果** | 玩家「我劝说守卫」→ AI 判定成功/失败/部分成功，并给出后果（见 §7） |
| **节奏控制** | 长时间无进展时主动抛钩子；高潮时收束为回合制；疲惫时提议存档休息 |
| **多人协调** | 识别不同玩家的角色，AI 在回复中@对应玩家推进剧情 |
| **OOC 守门** | 玩家戏外提问（「这个规则是什么」）AI 以主持人身份解答，不混入剧情 |

**与 agent.md 的差异**：

| 维度 | agent.md（验证） | gm-bot.md（上线） |
|------|------------------|-------------------|
| 触发方式 | 人类主持人发指令 | 玩家群消息自动触发 |
| 裁定 | 不替主持人裁定 | **必须**裁定（无人主持人） |
| 提案式交互 | 等主持人选择 | 改为：AI 自主推进 + 关键抉择时给玩家选项 |
| NPC 行动 | 仅在被要求时生成 | 主动驱动 |
| 持久化 | 写 data/ | 同（+ sessions/players/） |

### 4.4 持久化与会话

新增两个索引目录（其余复用）：

```
data/
├── sessions/<群号>.md      # 团会话状态：当前场景、在场者、进行中弧光、回合状态、最后活跃时间
└── players/<QQ号>.md       # 玩家绑定：绑定的角色 slug、显示名、权限
```

每次 AI 处理后，同步更新 `sessions/`（当前场景/轮次）与受影响的 `scenes/`、`story-arcs/`、`state-records/`。

## 5. 消息流（时序）

```
玩家A在群："我劝说守卫放我们进去"
   │
   ▼
NapCat 上报群消息事件
   │
   ▼
桥接服务：识别为 IC，查找群号→团会话，定位玩家A→角色
   │
   ▼
消息进聚合队列，启动 4s 等待窗口
   │  （窗口内玩家B又发："我在旁边帮腔" → 合并为一组）
   ▼
窗口结束，打包本轮玩家行动
   │
   ▼
构造 LLM 请求：系统提示词(gm-bot.md) + 上下文(场景+在场角色+当前弧光) + 本轮玩家行动
   │  （若已有正在处理的请求，本次排队，不并发）
   ▼
调用 LLM API
   │
   ▼
AI 返回：NPC反应 + 裁定结果 + 环境推进 + 可能的玩家选项
   │
   ▼
拆分回复 → 分段发回群（@玩家A、@玩家B）
   │
   ▼
持久化：更新 scenes/对话记录、按需写 state-records/、更新 sessions/轮次
```

## 6. 多人游戏与回合节奏

TRPG 传统是回合制，QQ 群天然是自由发言。**混合策略**：

| 场景类型 | 节奏模式 | 实现 |
|----------|----------|------|
| 探索/社交 | 自由发言 + 聚合 | 4s 窗口打包，AI 一次性响应所有人 |
| 战斗/紧张时刻 | 回合制 | AI 声明「进入回合制」后，改为按 `行动` 指令推进，每人一动作 |
| 关键抉择 | AI 给选项 | AI 抛出 2-3 选项，等对应玩家回复编号 |

**防淹没**：单个玩家短时间内连发多条 IC，AI 会在回复中提示「一次一个动作」并只处理最后一条。

## 7. 裁定机制

无人主持人意味着 AI 必须裁定。**两档方案**：

### 档位 A（验证/初版）：纯 LLM 判断
- AI 根据角色能力、行动难度、剧情需要、戏剧性综合判断。
- 适合轻规则、叙事向 TRPG。
- 实现简单，立即可用。

### 档位 B（进阶）：骰子 + LLM 解读
- 玩家声明行动 → AI 给出难度等级 → 后端掷骰（d20 等）→ AI 解读结果并演绎。
- 命运点/优势劣势等机制由 AI 在规则提示词中维护。
- 更硬核，但需投入规则提示词工程。

> 建议先上 A 档，跑通后再按需加 B 档。gm-bot.md 预留骰子接口。

## 8. 管理命令清单

通过群内 `/` 指令或私聊机器人触发：

| 命令 | 权限 | 作用 |
|------|------|------|
| `/开团 <团名>` | 管理员 | 在本群开启一个新团，初始化 sessions/ |
| `/结束团` | 管理员 | 结束并归档当前团 |
| `/绑定 <角色slug>` | 玩家 | 绑定自己的角色 |
| `/创建角色` | 玩家 | 引导式创建角色并建档到 data/characters/ |
| `/我的角色` | 玩家 | 查看自己绑定的角色卡 |
| `/回顾` | 玩家 | 让 AI 总结最近 N 轮发生了什么 |
| `/存档` | 管理员 | 手动触发一次全量持久化快照 |
| `/弧光` | 管理员 | 查看当前进行中的弧光列表与平衡报告 |
| `/暂停` `/继续` | 管理员 | 暂停/恢复 AI 自动推进 |
| `/设置 <key> <value>` | 管理员 | 调整等待窗口、发言间隔等参数 |

管理员通过私聊机器人执行敏感操作（配置 API Key、切换 LLM、导出存档）。

## 9. 部署方案

### 最小可用部署（单机）

```
一台常开机器（云服务器 / 家里的常开 PC / NUC）
├── NapCat            # QQ 登录（小号），常驻
├── 桥接服务(Node)    # 常驻，监听 OneBot，调 LLM，读写 data/
├── data/             # 即本项目 data/ 目录
└── config.env        # LLM API Key、QQ 账号、群号白名单
```

- 用 `pm2` / `systemd` 守护两个进程。
- `data/` 定期 git 提交或打包备份（存档即代码）。
- WorkBuddy 在开发机上连同一 `data/`（或拉取备份）做开发与复盘。

### 配置项（config.env）

```
LLM_API_BASE=https://...
LLM_API_KEY=sk-...
LLM_MODEL=glm-4-plus
QQ_BOT_UIN=10001xxx
TARGET_GROUPS=123456,789012
AGGREGATE_WINDOW_MS=4000
SEND_INTERVAL_MS=1000
ADMIN_QQ=1000admin
```

## 10. 实施路线图

| 阶段 | 产出 | 验收 |
|------|------|------|
| **P0 脚手架** | 桥接服务骨架：监听 OneBot、收发群消息、Echo 回群 | 机器人能在群里复读消息 |
| **P1 最小主持** | gm-bot.md 系统提示词 + LLM 调用 + 单玩家 IC→回复 | 单人对话能跑通一轮 TRPG |
| **P2 持久化** | sessions/players/ + 场景/弧光落地 + `/回顾` 生效 | 关掉服务重启后剧情不丢 |
| **P3 多人聚合** | 聚合队列 + 多人识别 + @回推 | 2-3 人同群游戏顺畅 |
| **P4 管理命令** | 开团/绑定/存档/弧光等命令 | 管理员能完整管理一个团 |
| **P5 节奏与裁定** | 回合制切换 + 裁定档位 A + OOC 守门 | 战斗场景可玩 |
| **P6 打磨** | 回复节奏、风控规避、长上下文压缩 | 长团不崩 |

> P0-P2 即可达到「能玩」；P3-P6 是体验打磨。

## 11. 风险与对策

| 风险 | 对策 |
|------|------|
| QQ 第三方协议风控/封号 | 小号、控频、避免短时大量消息、加随机延迟 |
| LLM 上下文膨胀 | 定期让 AI 总结历史写入 state-records/，对话只保留近期 + 摘要 |
| AI 裁定不公/出戏 | gm-bot.md 明确裁定原则；关键结果可被管理员 `/回退` |
| 多人同时行动冲突 | 聚合队列 + AI 在回复中明确先后顺序 |
| 服务挂掉 | pm2 守护 + data/ 持久化已落地，重启即恢复 |
| 玩家捣乱 | 管理员可 `/禁言 <QQ>` 暂停某玩家 IC 处理 |

## 12. 与验证系统的关系（复用清单）

| 验证阶段产物 | 上线阶段用途 |
|--------------|--------------|
| `agent.md` 工作流 | 抽取核心逻辑 → 扩展为 `gm-bot.md` 系统提示词 |
| `templates/*` | 原样作为 AI 生成内容的结构模板 |
| `data/characters` `npcs` `locations` `scenes` `items` `story-arcs` `state-records` | 原样作为运行时持久化目录 |
| 故事弧光四阶段结构 | 原样作为 gm-bot.md 的剧情骨架 |
| 角色三层模型、连接原则 | 原样作为 gm-bot.md 的一致性约束 |
| 验证场景 01/02/03 | 转为上线后的回归测试用例 |

**结论**：验证阶段不是废弃的原型，而是上线系统的「大脑与记忆层」。上线只新增「躯干」（QQ 接入 + 桥接服务）。

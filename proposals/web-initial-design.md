## 2. 玩家界面

### 2.1 核心交互模式

玩家界面的所有交互都通过「与 AI 主持人对话」完成，系统不设复杂的按钮/表单。

```
玩家输入文本 ─→ process_turn ─→ LLM 主持人处理 ─→ 回复流式推送
                                                      │
                   角色创建流 ←── 检测到未绑定角色 ─────┘
                   游戏对话流 ←── 已绑定角色
                   行动指导 ←── 玩家请求建议
```

### 2.2 角色创建对话

**触发条件**：玩家进入界面但尚未绑定角色。

**流程**：
1. 玩家输入概括叙述（如 _"我是个叛逃的帝国法师，带着一本禁书在港口躲藏"_）。
2. 后端调 `process_turn`（角色创建模式），内部走现有 `draft_character` 工具流。
3. LLM 主持人补全角色卡（外貌/性格/能力/背景/剧情钩子），落盘到 `data/characters/<slug>.md`（状态:待确认）。
4. 回复前端流式展示角色卡摘要 + 确认提示。
5. 玩家确认则绑定；玩家可要求修改（LLM 主持人按提示修改角色卡字段，落盘更新）。

**前端设计**：
- 对话式交互：玩家消息在左/下侧，AI 回复在右/上侧。
- 角色卡预览在回复中富文本展示（非纯文本，带排版、字段标签）。
- 确认按钮「确认创建」/「要求修改」嵌入在回复中。

**AI 辅助的交互原则**：
- 玩家只需给概括叙述，LLM 自动补全完整角色卡。
- 玩家可随时说「改一下外貌描写，更阴郁一些」——LLM 主持人直接修改对应字段并落盘。
- 不用在 UI 上展示所有字段让玩家填，全部走对话。

### 2.3 游戏对话

**触发条件**：玩家已绑定角色，处于某个场景中。

**流程**：
1. 玩家输入行动（如 _"我走向港务长办公室，敲了敲门"_）。
2. 后端调 `process_turn`（标准游戏模式），复用现有 GM 工具流。
3. LLM 主持人裁决/扮演 NPC/推进环境，回复通过 WebSocket 流式推送到前端。
4. 同时落盘到 `scenes/`、`state-records/` 等。

**前端设计**：
- 聊天界面风格（类似 ChatGPT / Discord），左侧场景信息面板。
- 场景信息面板显示：当前场景名称/描写、在场 NPC 列表、角色状态简表。
- 回复中的角色卡字段、NPC 名称加链接可点击查看详情。
- 场景切换时面板自动刷新。

**AI 辅助的交互原则**：
- 玩家只需输入角色行动的自然语言描述。
- LLM 主持人自动裁决、扮演 NPC、推进环境。
- 玩家可随时说「我刚才是想用魅力说服他，不是用威胁」——LLM 重裁。

### 2.4 扮演/行动指导

**触发条件**：玩家明确询问"我能做什么""有什么选择""接下来呢"。

**流程**：
1. 玩家输入 ↔ 系统检测为「查询请求」。
2. LLM 主持人基于当前场景/角色/弧光给出行动建议（不替代玩家决策）。

**前端设计**：
- 建议以选项列表形式展示（可点击快速输入）。
- 可与普通游戏对话无缝混合。

## 3. 备团编辑器

### 3.1 核心交互模式

所有操作通过「人类用简单提示指导 AI → AI 落地文档」完成。
不做复杂的拖拽式编辑器，全部是对话驱动的内容生成。

```
人类提示 ─→ LLM 编辑助手 ─→ 生成/修改文档落地到 data/
                            │
        规划故事线 ──────────┘
        创造角色 ────────────┘
        创造物品/道具 ────────┘
        创造场景/地点 ────────┘
```

### 3.2 规划故事线

**功能**：创建和编辑**主要弧光**（跨多场、备团用户预置的剧情骨架）。

**AI 辅助流程**：
1. 用户提示：_"设计一个港口走私团伙的主要弧光，风格偏 noir 犯罪"_。
2. LLM 编辑助手：
   - 按 `templates/story-arc.md` 生成四阶段结构（启程→矛盾积累→高潮→新的稳定）。
   - 标注级别=主要、规划者=备团用户。
   - 自动做平衡检查：检查与现有弧光是否冲突、是否触及红线。
   - 生成关联 NPC/地点/道具的占位条目。
3. 落盘到 `data/story-arcs/<slug>.md`。
4. 用户可继续提示调整：_"高潮部分改成法庭对峙而非枪战"_ → LLM 修改对应阶段并更新文档。

**辅助能力**：
- 查看已有弧光概览（读取 `data/story-arcs/` 列表，显示标题/阶段/状态）。
- 调整弧光阶段指针（进展/暂停/完成）。
- 检查弧光间交叉点与冲突。
- 导出弧光 DNA（四阶段摘要，供主持人快速查看）。

### 3.3 创造角色

**功能**：创建玩家角色或 NPC，落地到 `data/characters/` 或 `data/npcs/`。

**AI 辅助流程**：
1. 用户提示：_"创建一个港口守夜人队长，是个外冷内热的老兵"_。
2. LLM 编辑助手：
   - 按 `templates/character.md` 生成完整角色卡（外貌/性格/背景/能力/关系网/剧情连接）。
   - 判断类型（NPC vs 玩家角色），放到对应目录。
   - 动机/剧情钩子尽量挂接到已有弧光。
3. 落盘到 `data/npcs/<slug>.md` 或 `data/characters/<slug>.md`。
4. 用户可继续调整。

**辅助能力**：
- 查看已有角色列表。
- 将一个 NPC 升级为正式角色（补充缺失字段）。
- 批量生成一组 NPC（如"酒馆里的 5 个常客，各有特色"）。
- 修改角色卡任意字段。

### 3.4 创造物品/道具

**功能**：创建物品/道具，落地到 `data/items/`。

**AI 辅助流程**：
1. 用户提示：_"设计一把名为'潮汐之刃'的魔法剑，是走私团伙的信物"_。
2. LLM 编辑助手：
   - 生成物品描述、外观、特性、历史背景、剧情连接。
   - 挂接到对应弧光/角色。
3. 落盘到 `data/items/<slug>.md`。

### 3.5 创造场景/地点

**功能**：创建场景或地点，落地到 `data/scenes/` 或 `data/locations/`。

**AI 辅助流程**：
1. 用户提示：_"设计港口的地下黑市，一个有铁门把守的地下仓库区"_。
2. LLM 编辑助手：
   - 按 `templates/scene.md` 生成场景/地点描写。
   - 标注性质（主线/可回收/临时生成）。
   - 关联可在此场景出没的 NPC、可发现的道具。
3. 落盘到 `data/locations/<slug>.md`（地点）或 `data/scenes/<slug>.md`（具体场景）。

### 3.6 备团编辑器 vs 主持人的编辑范围

| 操作 | 备团编辑器（人类） | 主持人（AI） |
|------|-------------------|-------------|
| 创建主要弧光 | ✓ 规划四阶段 | ✗ 红线限制 |
| 创建单局/次要局部弧光 | ✓ | ✓ |
| 修改主要弧光阶段 | ✗（只推进） | ✗（只追踪推进） |
| 创建角色/NPC | ✓ 精细设定 | ✓ 当场补充（须一致） |
| 创建物品/地点 | ✓ | ✓ 支撑剧情 |
| 修改已有数据 | ✓ 全量编辑 | ✗ 仅追加（场景对话/状态记录） |

## 4. 主持人：全 AI 模式

### 4.1 设计思路

初步阶段不设「人类主持人界面」。主持人就是 AI bot，完全复用现有 QQ bot 的 GM 设计。

```
                     ┌──────────────────┐
 玩家消息 ──────────→│  process_turn    │
 备团编辑指令 ───────→│  (复用现有逻辑)   │
                     │   · 加载上下文    │
                     │   · LLM 工具循环  │
                     │   · 落盘          │
                     └────────┬─────────┘
                              │
                   ┌──────────┴──────────┐
                   │  SendMessage 协议    │
                   ├──────────────────────┤
                   │  QQ → matcher.send   │
                   │  Web → WebSocket 推送 │
                   └──────────────────────┘
```

### 4.2 两种消息来源的适配

`process_turn` 已是纯函数（见 `types.py` 的 `TurnInput`/`TurnResult`），接收 `SendMessage` 回调。适配点：

| 来源 | send_fn 实现 | 额外处理 |
|------|-------------|---------|
| QQ 群 | 包装 `matcher.send` | 消息分段（1900 字） |
| Web 玩家界面 | WebSocket 推送 | 流式发送、富文本格式 |
| Web 备团编辑器 | WebSocket 推送（系统消息通道） | 返回操作结果 + 文档预览 |

### 4.3 对话流与编辑流的区分

在后端通过 `TurnInput` 的扩展字段（或新增 `mode` 字段）区分三种流：

| 模式 | 用途 | LLM 侧重点 | 前端侧 |
|------|------|-----------|--------|
| `game` | 游戏对话 | 裁决/扮演/推进，走现有 GM 提示词 | 玩家界面聊天框 |
| `create_character` | 角色创建 | `draft_character` 工具优先，创建后切换 role | 玩家界面创建流 |
| `edit` | 备团编辑 | 替换系统提示词为「编辑助手」模式 | 备团编辑器界面 |

**编辑模式的系统提示词**（新写，不同于 `gm_runtime.md`）：

```
你是 ATRPG 的【编辑助手】，帮助备团用户规划和准备游戏内容。
你的职责：
1. 根据用户提示，按模板生成/修改故事弧光、角色、物品、场景的文档。
2. 每次生成或修改后，落地到 data/ 对应目录（通过 store 工具）。
3. 始终与已有数据保持一致——生成前检查现有弧光/角色/场景，避免冲突。
4. 弧光必须遵循四阶段结构，标注级别和规划者。
5. 可建议内容补充，但最终决定权在用户。

你**不是**游戏主持人，不扮演 NPC、不裁决行动、不推进剧情。
```

## 5. 前端技术方案

### 5.1 栈

| 层 | 选型 | 理由 |
|----|------|------|
| 框架 | React 19 + Vite | 生态丰富、团队熟悉度优先 |
| 路由 | React Router v7 | SPA 多页面 |
| 状态管理 | Zustand | 轻量、无 boilerplate、React 原生 |
| WebSocket | 原生 WebSocket API | 无额外依赖，后端是 FastAPI 原生 WS |
| CSS | Tailwind CSS v4 | 美观快速原型，与 React 生态契合 |
| Markdown 渲染 | react-markdown + rehype-sanitize | 角色卡/场景描写用 MD 渲染 |

### 5.2 页面结构

```
/login                  → 登录页（初期简单用户名/PIN 或免登）
/player                 → 玩家界面主页
  ├─ /player/chat       → 游戏对话（默认）
  └─ /player/character  → 角色卡查看
/editor                 → 备团编辑器主页
  ├─ /editor/arcs       → 弧光管理
  ├─ /editor/characters → 角色/NPC 管理
  ├─ /editor/items      → 物品管理
  └─ /editor/scenes     → 场景/地点管理
```

### 5.3 WebSocket 消息协议

```
客户端 → 服务端：
{
  "type": "chat" | "edit",
  "payload": { "text": "..." }
}

服务端 → 客户端：
{
  "type": "reply_chunk" | "reply_done" | "error" | "scene_update",
  "payload": { ... }
}
```

### 5.4 与现有控制台的关系

| 维度 | 现有控制台（console.py） | 新 Web SPA |
|------|------------------------|-----------|
| 定位 | 调试/历史查看/回滚 | 玩家+备团主交互界面 |
| 用户 | 开发者/管理员 | 玩家和备团用户 |
| 交互 | 只读查看+回滚 | 双向对话式交互 |
| 技术 | 内嵌 vanilla HTML | 独立 React SPA |

两者可共存——控制台保留为「后台管理」入口，SPA 作为主要前端。

## 6. 后端 API 设计

### 6.1 路由（FastAPI）

```
REST：
  GET    /api/info                    → 游戏基本信息（团名、状态、活跃角色数）
  GET    /api/character               → 当前玩家角色卡
  GET    /api/scene/current           → 当前场景信息
  GET    /api/history/turns?limit=N   → 最近 N 轮对话历史
  
  GET    /api/editor/arcs             → 弧光列表
  POST   /api/editor/arcs             → 新建弧光（通过 LLM 编辑助手）
  GET    /api/editor/arcs/{slug}      → 弧光详情
  PUT    /api/editor/arcs/{slug}      → 更新弧光
  
  # 以下资源同理（POST 走 LLM 辅助创建，PUT 走 LLM 辅助修改）：
  GET    /api/editor/characters       → 角色/NPC 列表
  POST   /api/editor/characters       → 新建角色（LLM 辅助）
  GET    /api/editor/items            → 物品列表
  POST   /api/editor/items            → 新建物品（LLM 辅助）
  GET    /api/editor/scenes           → 场景列表
  POST   /api/editor/scenes           → 新建场景（LLM 辅助）
  GET    /api/editor/locations        → 地点列表
  POST   /api/editor/locations        → 新建地点（LLM 辅助）

WebSocket：
  WS     /ws                          → 游戏对话 + 备团编辑（根据 auth 区分）
```

### 6.2 编辑操作的 LLM 辅助流程（以新建弧光为例）

```
POST /api/editor/arcs  Body: { "prompt": "设计一个港口走私团伙的弧光" }

后端：
1. 读取当前已有弧光列表（避免冲突）
2. 构建编辑助手 system prompt（含已有数据摘要）
3. 调 LLM，传入用户 prompt
4. LLM 返回弧光文档内容（含 meta 和 body）
5. 校验：级别合规、不与已有冲突
6. 落盘到 data/story-arcs/<slug>.md
7. 返回：{ slug, title, 文档预览, 建议继续调整的提示 }

用户可继续 PUT /api/editor/arcs/{slug}  Body: { "prompt": "高潮改成法庭对峙" }
→ LLM 读取现有文档，按提示修改对应部分，重新落盘。
```

## 8. 实施步骤

### Step 1：后端 API 基础
1. 从 `console.py` 提取 FastAPI app（或新建 `web_api.py`），独立于 NoneBot 启动。
2. 实现 `GET /api/info`、`GET /api/character`、`GET /api/scene/current`（复用 store）。
3. 实现 `WS /ws` 基本框架（认证 + 消息路由）。
4. 在 WebSocket handler 中调用 `process_turn`，用 WebSocket.send 作为 send_fn。

### Step 2：玩家界面前端
1. 用 React + Vite 初始化前端项目 `frontend/`。
2. 实现聊天界面组件（消息列表 + 输入框 + WebSocket 连接）。
3. 实现角色创建对话流程。
4. 实现侧边场景信息面板。

### Step 3：备团编辑流
1. 新增编辑助手的 system prompt（`gm_runtime.md` 同级或同文件扩展）。
2. 在 `process_turn` 中支持 `mode="edit"`（替换 system prompt）。
3. 实现弧光/角色/物品/场景的 REST 查询接口。
4. 实现 POST/PUT 接口走 LLM 辅助生成。
5. 备团编辑器前端页面（列表 + 详情 + 对话式编辑）。

### Step 4：集成与优化
1. 前端的错误处理、加载状态。
2. 角色卡富文本渲染（react-markdown + CSS）。

## 9. 与现有 QQ Bot 的关系

```
                    ┌──────────────────────┐
                    │  共用核心             │
                    │  store.py            │
                    │  arc.py              │
                    │  llm.py              │
                    │  gm_runtime.md       │
                    │  工具表（14个）       │
                    └──────────┬───────────┘
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
   ┌──────┴──────┐    ┌───────┴───────┐   ┌───────┴───────┐
   │ QQ Bot      │    │ Web 玩家界面  │   │ 备团编辑器   │
   │ (NoneBot)   │    │ (React SPA)  │   │ (React SPA)  │
   │ 群消息入口   │    │ WS + REST    │   │ REST + LLM   │
   └─────────────┘    └───────────────┘   └───────────────┘
```

- QQ Bot 和 Web 前端共享同一游戏目录（`data/`），同一角色的 QQ 和 Web 操作互见。
- `process_turn` 是唯一入口，Web 和 QQ 都调它。
- 备团编辑器的落盘内容（弧光/角色/物品/场景）立即可被 QQ Bot 读取使用。

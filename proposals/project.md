# ATRPG Project

ATRPG（名称暂定）的目标是实现一个 AI 可以参与任何 TRPG 环节的系统。
核心愿景有二：
- 让主持人从复杂的故事创作劳动中解放，降低主持人的创作负担，从而能够制作出更丰富更有质量的针对同桌玩家的内容。
- 让主持人和玩家即使扮演能力堪忧，也能在 AI 的帮助下表现出富有创意和深度的角色扮演。

它的核心场景有：
- 作为现场 TRPG 的补足，提供剧情编写和角色扮演的辅助。
- 作为 TRPG 平台，提供在线的角色扮演和剧情体验。
- 作为独立的 TRPG 平台，允许玩家在没有主持人的情况下进行游戏。也允许让 AI 代替某个玩家进行游戏。

初步的计划是，实现一个可以编写 TRPG 剧情、管理角色信息，并在游戏过程中提供 AI 辅助的系统。

---

## 角色与职能

系统中的角色分为四类，职责边界清晰：

### 备团用户（人类）
负责内容生产，**在游戏运行前**工作：
- 规划**主要故事弧光**（高层次、跨多场、影响整体走向的剧情骨架）。
- 准备玩家角色、核心 NPC、地点、世界设定、关键道具。
- 设定世界基调与规则风格。
- 备团用户**不参与现场运行**，其产出作为主持人运行的输入与约束。

### 主持人（AI bot）
负责现场运行，**在游戏过程中**工作：
- 现场调配故事、扮演 NPC、裁决玩家行动、推进环境。
- 可规划**次要局部弧光**与**单局弧光**（见下文弧光分级），为剧情提供即时的小冲突与任务。
- **不可设计高层次（主要）弧光**——主要弧光由备团用户预置，主持人只在其内运行并追踪演化。
- 在"AI 完全代替主持人"的运行模式下，主持人即 AI bot 本身。

### 玩家（人类，群成员）
- 提供角色资料，可指定一个角色为自己扮演的角色。
- 通过 @bot 声明行动，进行角色扮演。

### 管理员（人类）
- 主要是一个远程配置角色：管理系统文件、配置 API Key、设定各个系统参数。
- 不参与剧情与扮演。

## 故事弧光分级

所有剧情都遵循四阶段故事弧光结构：**启程 → 矛盾积累 → 高潮 → 新的稳定**。弧光按尺度分三级：

| 级别 | 定义 | 典型形态 | 规划权 |
|------|------|----------|--------|
| **主要弧光**（高层次） | 跨越多场；涉及核心 NPC/世界观/阵营势力；影响整体走向 | 港口走私大案、王国阴谋、神祇复苏 | 备团用户 |
| **单局弧光** | 一个任务、一段冒险；设计上对应实际 TRPG 中 1~3 次聚会用的故事弧光 | 一次地城探索、一个委托任务、一段支线冒险 | 主持人 |
| **次要局部弧光** | 单一场景内的局部互动；局部性非常强 | 与商店老板讨价还价、酒馆里的一次闲聊 | 主持人 |

**关键说明**：
- 次要局部弧光**甚至不需要真正有个弧光收尾**——它可能只是开始了一段小互动，下次玩家再到该场景时（如再次光顾那家商店）可以继续。
- 单局弧光是 TRPG 的常见故事单元，一次冒险/任务的体量。
- 弧光可相互交叉（一个弧光的高潮期，另一个弧光的启程可同时发生）。
- 必须区分主次，不能让过多程度相当的弧光同时发生，以免剧情混乱。
- 弧光可随玩家选择动态调整——当玩家做出重大选择时，重新评估受影响弧光的阶段与走向（但主要弧光的结构调整权在备团用户）。

## 初步场景

- 玩家通过玩家界面（或 @bot），发送消息，"我准备劝说这个 NPC"——系统会根据玩家的意图和角色信息，生成玩家自己角色的扮演内容，并将其呈现给玩家。
- 备团用户通过备团界面，发送消息，"玩家进入（一个城市地点），设计一个故事线"——系统会根据故事风格，按照故事弧光结构生成相应的剧情内容。
- 主持人通过主持人界面（或 AI bot 自动），发送消息，"玩家团队获得了（关键道具）"——系统会记录相关的游戏状态变化。
  - 不是简单的记录数据，要针对相关的故事弧光形成连接，记录其对故事发展的影响和变化。
  - 主持人可以要求系统根据已有设定设计一个场景、角色、剧情片段。
    - 在实际中，这些可能是临时的（例如玩家想找街边的某种商店，或者临时需要一个路人 NPC），主持人对这种临时需求常常选择简化，这里希望系统能提供描写丰富有趣的内容。
    - 生成内容必须与已有的故事设定和角色信息保持一致，确保剧情的连贯性和合理性。
    - 所有的生成内容，包括临时场景、角色和剧情片段，都必须要持久化落地，以便在后续的游戏过程中能够被引用和影响剧情发展。

## 实现阶段

### 初步验证阶段
使用 `agent.md` 文件实现一个初步流程验证，验证场景的可行性和系统的基本功能。并不涉及代码开发和完整系统的实现。详见 `agent.md` 与 `scenarios/`。

### 运行时验证阶段
让 AI 完全代替主持人，在一个符合 `agent.md` 规划的目录上运行，接入 QQ 群 bot 担任主持人，开放游戏模式。详见 `proposals/qq-runtime-design.md`。

---

## 实现阶段技术性要求

- 使用网页技术实现，包括前端界面和后端逻辑处理。前端负责玩家和主持人的交互界面，后端负责剧情生成、角色管理和游戏状态记录。AI 请求应当是排队在后端处理，不能像酒馆那样前端关闭就中断请求。
- 角色分为四类（见上"角色与职能"）：备团用户 / 玩家 / 主持人（AI）/ 管理员。
- 所有的上下文和配置都位于一个项目路径。
- **QQ Bot 连接与 API 配置**：参考 [openhanako](https://github.com/liliMozi/openhanako) 项目的做法——
  - 使用腾讯 **QQ 官方 Bot API**（appID + appSecret → access_token 鉴权），通过 WebSocket 接收事件、REST API 发送消息，群聊经"@消息"事件触发。
  - API 配置采用单一配置文件（如 `config.yaml`）+ 模型 providers 多商管理；模型按用途分类（对话模型 / 工具模型 / 大工具模型等）。
